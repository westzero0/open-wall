# 공지는 자동으로 감지하고 게시는 사람이 승인한다

*기준일 2026-10-18 · 대상: 해벽(haebyeok.app) 인공암벽장 63곳 · 독자: 1인 유지보수자*

## 1. 요약

1. **가능하다. 단 "감지"와 "게시"를 분리해야 한다.** 공지 게시판·블로그 RSS를 낮은 빈도로 읽어 "새 글이 올라왔다"를 알아내는 일은 무료 서버리스(GitHub Actions 중심)로 실현할 수 있다. 휴관·시간·요금 같은 값은 LLM이 추출하더라도 사람이 승인해야 `data/national.json`에 들어간다.
2. **자동 게시는 "공지 있음 + 원문 링크 + 확인 시각"까지만 허용한다.** 이 문구는 휴관을 단정하지 않는다(키워드만으로는 "휴관"과 "휴관 아님"을 구분하지 못한다).
3. **수집 우선순위는 (a) 암장 자체 홈페이지·지자체/공단 게시판 HTML, (b) 네이버 블로그 RSS, (c) 그 밖의 링크 제공이다.** 인스타그램·카카오 채널·네이버 플레이스·카페는 안정적이고 약관에 맞는 읽기 경로가 없다. 링크만 제공하고, 암장이나 이용자의 제보로 보완한다.
4. **가장 큰 미지수는 실행 환경의 IP가 한국 사이트에 차단되는지다.** GitHub 러너(Azure 대역)와 Cloudflare Worker 모두 해외 IP다. 63개 URL로 실측하기 전에는 설계를 확정하지 않는다.
5. **법적 위험은 낮은 빈도, 우회 없음, 사실만 저장, 원문 링크 노출, 차단되면 중단, 옵트아웃 제공으로 대부분 줄일 수 있다.** 다만 판례·약관 내용은 모두 2차 요약에 기댄 것이라 변호사 확인이 필요하다.
6. **비용은 대략 월 0~25달러로 추정한다. 병목은 비용이 아니라 사이트별 파서 유지보수와 검수 시간이다.** 63곳 중 파서가 필요한 곳을 먼저 세어 보고, 검수는 하루 1회 묶음 PR로 처리한다.
7. **첫 2주 안에 세 가지를 해 본다.** 63개 URL을 두 실행기에서 호출해 차단율을 측정한다. robots.txt와 약관을 점검한다. 정답 세트 100건을 만든다. 이 결과가 나쁘면 "링크 제공 + 제보" 모델로 후퇴한다.

## 2. 이 보고서의 근거 한계 (먼저 읽을 것)

조사원들은 대부분 원문 페이지를 열지 못했다. DNS 실패나 프록시 차단(403) 때문이다. 아래 수치와 법적 서술은 **검색 결과 요약(2차 출처)** 에서 가져왔고, 직접 확인한 것은 Anthropic 문서 일부뿐이다. 이 보고서는 서술마다 다음 라벨을 붙인다.

- **[출처]** 노트에 인용 URL이 있는 발견. 원문 재확인 전에는 "요약으로 보고된 사실"이다.
- **[추론]** 조사원 또는 필자의 설계 추론. 근거 문헌이 없다.
- **[공백]** 확인하지 못한 사항.

설계를 확정하기 전에 **라이브 페이지에서 재검증해야 하는 항목**은 다음과 같다.

| 항목 | 노트의 값 | 재검증이 필요한 이유 |
|---|---|---|
| Workers 무료 한도 | 크론 5개, subrequest 50, 크론당 CPU 10ms ([Workers limits](https://developers.cloudflare.com/workers/platform/limits)) | 검색 요약 기반. 유료 subrequest는 오래된 캐시 1,000 vs 현재 10,000으로 **노트 내 값이 갈린다** |
| Browser Rendering | 무료 하루 10분, 동시 3개 ([BR limits](https://developers.cloudflare.com/browser-rendering/limits/)) | 새 인스턴스 한도가 "분당 3회"(구) vs "20초당 1회"(신)로 **갈린다**. 제3자 계산기는 다른 값을 주장(무시) |
| GitHub Actions | 공개 저장소 무제한, 60일 무활동 시 스케줄 비활성 | 2차 출처와 GHES 문서 사본만 확보. 봇 커밋이 "활동"으로 인정되는지 미확인 |
| 네이버 검색 API(API HUB) | 신규 신청 2026-07-30/31 중단(**출처마다 하루 차이**), 특약 2026-09-07 시행(한 기사는 "20일"), 일 25,000회 | 모두 언론·블로그 2차 출처. 특약의 **저장·캐시 금지 여부는 출처 간 충돌**(TokenPost는 금지 보도, 다른 확인에서는 명시 조항 못 찾음) |
| 대법원 2021도1533 | 여기어때 사건 무죄 확정, DB권·침입·업무방해 불인정 | 판결문 원문 미열람. **세계일보 등 일부 기사는 침입·업무방해를 인정한 것처럼 읽히며** 사건번호 2020도17860은 미확인. 최우선 재확인 |
| 그 밖의 판례·조문 | 2023도1086, 2014다235080, 잡코리아-사람인, 부경법 제2조 제1호 카목, 저작권법 제7조·제24조의2 | 모두 요약 수준 또는 [미검증]. 조문 번호는 law.go.kr에서 확인 |
| 모델 가격 | Claude Haiku 5.5 입력 $0.10 / 출력 $0.50 per MTok, Haiku 4.5 $1/$5 ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)) | 요약 모델을 거친 값이고 10배 차이라 의심스럽다. OpenAI·Gemini 가격은 모두 집계 사이트 값(저신뢰) |
| 부가 서비스 한도 | Healthchecks 무료 20개, Resend 무료 일 100건(도메인 수 1 vs 3 충돌), Apps Script 일 90분 | 2차 출처 |

원문을 확인한 사실은 두 가지뿐이다. Anthropic 문서의 "환각 기법은 환각을 완전히 없애지 못한다" 및 구조화 출력 관련 서술이 하나다([Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)). 구조화 출력이 형식만 보장한다는 점이 다른 하나다([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)).

이 보고서는 법률 자문이 아니다.

## 3. 채널별 실현 가능성: 자체 사이트와 블로그 RSS만 쉽다

판정은 필자의 종합이다(노트 §7의 순위를 따르되 일부 조정). 근거는 각 행의 출처다.

| 채널 | 판정 | 이유 |
|---|---|---|
| 암장·지자체·공단 자체 홈페이지 공지 HTML | **보통** (사이트당 쉬움, 63곳 합치면 품이 듦) | 서버 렌더링 목록 + 번호 diff로 충분한 곳이 많다고 [추론]. 서울시설공단은 `bbsMsgList.do?bcd=notice` 형태 목록 ([sisul.or.kr](https://www.sisul.or.kr/open_content/parking/bbs/bbsMsgList.do?bcd=notice)). 사이트별 선택자 유지가 진짜 비용, 해외 IP 차단 가능성 |
| 네이버 블로그 RSS | **쉬움** | `rss.blog.naver.com/{blogId}`, 키 불필요. 단 글쓴이의 "외부 보내기 허용" 설정에 의존 ([extrememanual](https://extrememanual.net/6386), 저품질 출처). 2025-12-04 HTTP/1.0 차단은 Workers·curl에 영향 없을 것으로 [추론] (2차 출처만) |
| 티스토리·워드프레스 등 일반 블로그 피드 | **쉬움** | `<link rel="alternate" type="application/rss+xml">` 자동 탐색. 2026년 상태는 [공백] |
| JS 렌더링 게시판 | **보통** | Playwright를 GitHub Actions에서 쓰거나 Browser Rendering 사용. 무료 10분/일이면 하루 60페이지 안팎이라 소수 사이트에만 맞음 |

| 공공데이터포털·열린데이터 | **쉬움, 가치 낮음** | 공공체육시설 파일(15131856)에 휴관일 필드가 있으나 연 단위 정적 자료 ([data.go.kr](https://www.data.go.kr/data/15131856/fileData.do)). 임시 휴관·공사·요금 공지는 없다. 암장 전용 데이터셋도 확인 못 함 |
| 네이버 플레이스 "소식" | **비현실** | 공식 API 없음, 자동 수집은 네이버 약관·robots와 충돌 ([socialcrawl](https://www.socialcrawl.dev/ko/blog/naver-crawling), 이해관계 있는 출처) |
| 네이버 카페 | **비현실/불명** | RSS 근거 없음, 회원 전용이 많음 [공백] |
| 인스타그램 | **비현실 (링크만)** | Basic Display API는 2024-12-04 종료 ([getphyllo](https://www.getphyllo.com/post/instagram-basic-display-api-deprecation-what-it-is-for-developers-and-businesses)). Graph API는 본인 또는 권한 부여 계정 중심, Business Discovery는 출처마다 서술이 갈려 미검증. 스크래퍼는 로그인 필요, IP 변동 시 계정 차단 사례 ([coop-cloud rsshub](https://git.coopcloud.tech/coop-cloud/rsshub/raw/branch/main/README.md)). 인스타그램은 이 앱의 가장 큰 사각지대다. 작은 암장은 인스타그램에만 공지를 올리는 경우가 많다고 조사원은 [추론]한다. 63곳 중 몇 곳이 여기에 속하는지 먼저 세어 보아야 한다. 이 곳들은 자동 감지가 아니라 제보와 수동 확인으로 처리한다.

## 4. 권장 아키텍처: GitHub Actions가 읽고, 사람이 PR로 승인한다

핵심 선택은 세 가지다. 첫째, **실행기는 GitHub Actions 스케줄을 기본으로 한다.** 공개 저장소에서 무료·무제한 분이라고 보고됐고([cicdcost](https://cicdcost.com/github-actions-pricing), 2차 출처), 상태 JSON을 커밋하면 변경 이력이 곧 감사 로그가 된다("git scraping", [Willison](https://simonwillison.net/2020/Oct/9/git-scraping/)). 둘째, **Cloudflare Worker는 보조로 둔다.** 이미 있는 Worker를 알림 웹훅이나 대체 실행기로 쓴다. 무료 플랜은 subrequest 50개, 크론 CPU 10ms라서 63곳을 한 번에 파싱하기 빡빡하다([Workers limits](https://developers.cloudflare.com/workers/platform/limits)). 셋째, **LLM에는 도구도 쓰기 권한도 주지 않는다.** PR을 여는 것은 별도의 제한된 토큰이고, 병합은 사람만 한다.

```
[sources.yml: 암장 63곳 × {유형, URL, 파서, 주기, robots 결과, 상태}]
        │
        ▼  (GitHub Actions cron, 분 단위는 :17처럼 정시 회피)
┌──────────────────────────────────────────────────────────┐
│ 1. fetch  : 고유 UA, robots 준수, 동일 호스트 동시 1건,     │
│             ETag/If-Modified-Since, 실패 시 백오프          │
│ 2. parse  : 목록 행 → (item_key, 제목, 게시일, 링크)        │
│             RSS는 피드 항목을 그대로 사용                   │
│ 3. diff   : state/<source>.json의 seen-set과 비교          │
│             → 신규 항목만 다음 단계 (첫 실행은 기준선만 저장) │
│ 4. flag   : 키워드+날짜 정규식 → 우선순위 (high/low/none)    │
└──────────────────────────────────────────────────────────┘
        │ 신규 + high/low                         │ 모든 신규
        ▼                                         ▼
┌────────────────────────────┐        ┌──────────────────────────┐
│ 5. LLM 추출 (high만, 선택)  │        │ Tier 1 자동 게시:         │
│  - 도구/비밀/쓰기권한 없음   │        │ "공지 있음 · 제목 · 날짜  │
│  - 스키마 강제 + 증거 인용   │        │  · 원문 링크 · 확인시각"  │
│  - 결정론적 검증(인용 일치,  │        │ (휴관 단정 금지)         │
│    날짜 범위, 시설명 매칭)   │        └──────────────────────────┘
└────────────────────────────┘
        ▼
┌──────────────────────────────────────────────┐
│ 6. 묶음 PR (하루 1회): national.json 제안 diff│
│    + 원문 링크 + 증거 인용 + 모델 ID + 플래그  │
│    → 유지보수자가 검토·병합 = 승인 (Tier 2)    │
└──────────────────────────────────────────────┘
        ▼
[알림] GitHub 앱/메일(기본) · 선택: Telegram
[감시] 실행 종료 시 Healthchecks.io ping, 실패 시 /fail
```

**상태 저장**은 저장소의 JSON 파일(소스별)로 시작한다. 무료, 사람이 읽을 수 있고, 변경 이력이 남기 때문이다. 단점은 커밋 소음과 쓰기 경합이므로 한 워크플로가 직렬로 쓰게 한다[추론]. 질의가 필요해지면 Cloudflare D1 무료(일 읽기 500만 행, 쓰기 10만 행, 저장 5GB)로 옮긴다([D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)). KV는 무료 쓰기가 하루 1,000회라 "변경 시에만 쓰기"를 지켜야 한다([KV pricing](https://developers.cloudflare.com/kv/platform/pricing)).

**한국 IP 문제의 대비책.** 실측에서 차단이 확인되면 순서대로 (1) Worker에서 해당 사이트만 호출, (2) Apps Script 시도(미국 IP라 같은 문제 가능, 확인 필요), (3) 한국 리전 소형 VM(네이버 클라우드 마이크로 서버 등, 비용 [공백])을 고려한다. 프록시나 IP 회전은 법적으로 불리하게 읽히므로 쓰지 않는다(§6).

**제외한 대안.** changedetection.io·urlwatch는 성숙한 도구지만 상시 호스트가 필요하다([changedetection.io](https://github.com/dgtlmoon/changedetection.io), [urlwatch](https://github.com/thp/urlwatch)). 서버리스라는 제약과 맞지 않으므로 한국 IP 문제로 VM을 쓰게 될 때의 대안으로 남겨 둔다. Visualping 무료(5페이지)와 Distill 무료(출처 간 값이 갈림)는 63곳에 부족하다. 기타 SaaS 한도는 라이브 페이지에서 확인해야 한다.

## 5. 단계별 도입안: 자동은 "감지"까지, 값은 사람이 승인

| 단계 | 기간(추정) | 자동으로 하는 것 | 사람이 승인하는 것 |
|---|---|---|---|
| **0. 검증** | 1~2주 | 없음(실험만) | 실험 결과로 go/no-go 결정 (§9) |
| **1. MVP: 감지 + 알림** | 2~3주 | 공지 URL 보유 암장 중 RSS·단순 HTML 소스를 폴링. 신규 글 발견 시 유지보수자에게 묶음 알림. 각 암장 `checked_at`은 갱신하지 않음(감지 ≠ 확인) | 모든 반영. 유지보수자가 링크를 열어 보고 `national.json`을 직접 수정 |
| **2. 공개 플래그** | +2주 | 신규 글이 키워드 규칙에 걸리면 앱에 "공지 있음 · 원문 보기 · N일 전 확인" 표시. 문구는 단정 금지 | 오탐으로 판명된 플래그의 수동 해제. 키워드 목록 조정 |
| **3. 제안 diff (LLM)** | +3~4주 | LLM이 high 우선순위 공지에서 구조화 값을 추출하고 결정론적 검증을 통과한 것만 묶음 PR의 제안 diff로 생성 | **PR 병합 = 승인.** 휴관·시간·요금 값은 전부 사람이 본다 |
| **4. 확장** | 이후 | 소스 추가(블로그 RSS, JS 사이트), 네이버 검색 API를 "힌트"로 추가(특약 확인 후), 만료 자동 복귀(승인된 임시 휴관은 종료일 후 정규 운영으로 결정론적 복귀) | 만료 후 "재개관" 확인, 월 1회 표본 감사 |

휴관·공사 같은 안전 관련 사실은 단계가 올라가도 자동 게시하지 않는다. 틀린 "정상 운영"은 헛걸음을, 틀린 "휴관"은 이용 기회 상실을 낳는다. LLM 오류는 형식이 멀쩡해서 사후에 발견하기 어렵다([추론], 노트 LLM §4). 자동 병합 완화는 몇 달치 감사 데이터(두 번 추출·정규식·규칙이 모두 일치하고 위험이 낮은 "재개관" 같은 범주)가 쌓인 뒤에나 검토한다.

### `national.json` 필드 매핑 제안 (사람이 승인하는 diff)

코드베이스에 대해 알려진 것은 암장별 `contact.notice_url`, `blog_posts`, `exceptions`, `suspended`, `checked_at` 필드뿐이다. 필드의 실제 스키마(타입, 날짜 형식)는 확인하지 못했으므로 아래는 **개념적 제안**이며 실제 구조에 맞춰 조정해야 한다.

| 감지 결과 | 제안 변경 | 자동/승인 |
|---|---|---|
| 소스 등록 | `contact.notice_url`이 비었으면 후보 URL 제안. 기존 값과 다르면 변경 제안 | 승인 |
| 신규 공지 발견(분류 무관) | 앱의 "공지 있음" 플래그와 원문 링크(앱 쪽 필드나 별도 상태 파일로 두는 것을 권장. 기존 필드 의미를 바꾸지 않기 위함) | 자동 |
| 블로그 글이 공지 성격 | `blog_posts`에 항목 추가 제안(제목·URL·게시일, 본문 전문 제외) | 승인 |
| 임시 휴관·시간 변경·공사 | `exceptions`에 기간 항목 제안(시작·종료·사유·원문 링크). 증거 인용과 함께 | 승인 |
| 전면 중단/운영 중단 | `suspended` 변경 제안 | 승인 |
| 재개관 공지 | `suspended` 해제와 관련 `exceptions` 종료 제안 | 승인 |
| 요금 변경 | 요금 필드 변경 제안(또는 "확인 필요" 표시만) | 승인 |
| 사람이 확인 완료 | `checked_at` 갱신 | **사람만**(자동 갱신 금지: "봇이 읽었다"를 "검증했다"로 오해시키지 않기 위해 [추론]) |

PR 본문에는 암장명, 원문 링크, 게시일, 증거 인용(원문에서 그대로), 모델 ID, 경고 플래그, 변경 전후 JSON diff를 넣는다. 항목당 1분 안에 판단할 수 있게 하고, 하루 1회 묶음으로 올려 알림 피로를 줄인다([추론]).

## 6. 법적·약관 체크리스트 (설계 원칙, 법률 자문 아님)

판례·약관은 전부 2차 요약이다. **변호사 확인 필요**로 표시한 항목은 배포 전에 원문과 전문가 검토를 거쳐야 한다.

방향성만 정리하면 이렇다. 공개 페이지를 사람이 볼 수 있는 수준으로 가끔 읽는 것은 형사 위험이 낮은 쪽이라고 보도된다. 대법원 2021도1533에서 정보통신망 침입·DB권 침해·업무방해(약 1,594만 회 호출)에 대해 무죄가 확정됐다는 요약이 다수 출처와 일치한다([Daum 요약](https://v.daum.net/v/Fi3RbZBWW5), [lawtalk](https://www.lawtalk.co.kr/posts/171714)). **그러나 이 판결 결과는 출처 간 충돌이 있어 [미검증]** 이다([세계일보](https://www.segye.com/newsView/20210427512517)). 민사(약관 위반)와 부정경쟁 위험은 별개다. 잡코리아 대 사람인 사건에서는 VPN 분산과 robots.txt 미확인이 불리하게 소개됐다([Byline Network](https://byline.network/2016/02/1-64/)). 최종심 결과는 확인하지 못했다.

## 7. 오탐·미탐·모니터 고장 관리

### 변경 감지 기법: 목록 항목 기준이 가장 안정적이다

전체 페이지 해시나 텍스트 diff는 광고·조회수·"N일 전"·방문자 수 때문에 소음이 가장 크다는 것이 일관된 서술이다([PageCrawl](https://pagecrawl.io/help/reduce-false-positives/article/reduce-false-positives-monitoring-website-for-changes), 벤더 출처). 따라서 **게시판 행의 (번호 또는 링크 키, 정규화된 제목, 게시일)만 비교한다**. 키는 게시글 번호이고, 없으면 제목+날짜의 해시다. 고정 공지(공지 고정 행은 번호가 숫자가 아님)와 제목 수정은 낮은 심각도의 별도 이벤트로 처리한다. 이상은 모두 [추론]이며 측정된 오탐률은 어떤 기법에도 공개된 것이 없다. 단일 공지 상세 페이지의 본문 비교에는 본문 추출기(Trafilatura 등)를 쓸 수 있지만 한국어 게시판에 대한 평가는 없다([Trafilatura 평가](https://trafilatura.readthedocs.io/en/latest/evaluation.html), 자체 평가). EUC-KR 인코딩 처리는 직접 테스트한다.

### 오탐 관리

- **첫 실행은 기준선만 저장하고 알리지 않는다.** 한 번에 신규 10건 이상이 한 소스에서 나오면 보류하고 파서 변경 의심으로 처리한다.
- **오탐 라벨**(조회수, 상대 날짜, 고정글 재등장, 수정글, 파서 오류)을 PR·이슈에서 붙이고 소스별 오탐률을 센다. 목표 5% 미만, 10% 초과 소스는 선택자를 고친다(수치는 [추론]).
- **일주일은 느슨하게 돌리고 이후 임계값을 조인다**는 조언이 있다([Apify Dataset Drift](https://apify.com/cynix_dev/dataset-drift-qa), 벤더).

### 미탐 관리: 가장 어렵고 가장 중요하다

1. **키워드 안전망**: LLM이 "해당 없음"이라 해도 키워드+날짜 정규식이 맞으면 검수로 보낸다. 재현율을 정밀도보다 우선한다.
2. **월 1회 표본 감사**: 무작위 10개 소스를 사람이 직접 열어 감지 목록과 비교한다. "다른 곳에서 알게 됨" 기록을 남긴다.
3. **STALE 카나리**: 소스의 과거 최대 게시 간격보다 오래 새 글이 없으면 "고장났거나 정말 조용함"으로 표시한다.
4. 감지 지연(첫 발견 시각 − 게시일)을 이벤트 표에 기록한다.

### 소스별 상태와 모니터 고장 알림

"가져오기 실패", "파싱 0행", "변경 없음"은 세 가지 다른 상태다([ScrapeGraphAI](https://scrapegraphai.com/glossary/ai-scraping/self-healing-scrapers)의 "무음 오염이 빈 결과보다 나쁘다"는 취지와 일치). 상태는 `OK / FETCH_ERROR(타임아웃·5xx·429·로그인/타 도메인 리디렉션) / PARSE_BROKEN(0행 또는 중앙값 대비 50% 미만, 필수 필드 공백) / STALE`로 나눈다. 실패는 재시도 2~3회 후에 세고, 연속 3회 또는 24시간 이상일 때만 유지보수자에게 알린다. 일일 한 건의 "모니터 건강" 요약("63곳 중 58곳 정상, 오류 2, 신규 3")으로 묶는다(전부 [추론]). 소스를 등록할 때 HTML 샘플과 기대 행을 골든 픽스처로 저장해 선택자 변경을 회귀 테스트한다.

스케줄러 자체의 죽음은 외부 데드맨 스위치로 잡는다. 실행 끝에 Healthchecks.io를 ping하고(무료 20개로 보고됨, [freetier.co](https://freetier.co/directory/products/healthchecksio)) 실패 시 `/fail`을 보낸다([문서](https://hc.oceanx.org/docs/)). 이는 GitHub의 지연·누락, 공개 저장소의 60일 무활동 비활성([GHES 문서](https://docs.github.com/en/enterprise-server@3.13/actions/how-tos/managing-workflow-runs-and-deployments/managing-workflow-runs/disabling-and-enabling-a-workflow))도 외부에서 탐지한다. 크론은 최선 노력이고 정시 부하가 높으므로 `:17`처럼 비정시 분을 쓴다([GHES 스케줄 문서](https://docs.github.com/de/enterprise-server@3.4/actions/managing-issues-and-pull-requests/scheduling-issue-creation)). 봇 커밋이 60일 규칙의 "활동"으로 인정되는지는 미확인이므로 월 1회 사람의 활동(PR 검토)에 기대거나 keepalive를 둔다.

### LLM 추출: 정확도는 "측정 전까지 미지수"

한국어 시설 공지에 대한 추출 정확도를 보고한 연구는 찾지 못했다 [공백]. 근접 증거(영어·임상 텍스트)는 구간 탐지는 강하지만 상대 날짜 정규화가 약하다고 말한다([Frontiers 2022](https://www.frontiersin.org/journals/research-metrics-and-analytics/articles/10.3389/frma.2022.1001266/pdf)). 구조화 출력은 JSON 형식을 보장할 뿐 값의 정확성은 보장하지 않는다([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). 시험해 볼 실패 유형은 연도 생략("10.20~10.25"), 상대 날짜의 기준일 오류, 종료일과 재개관일의 하루 차이(원주 사례: 5/1까지 휴관, 5/2 재개, [syu.ac.kr 검색 요약](https://www.syu.ac.kr/blog/%ec%88%9c%ec%b2%9c%ec%8b%9c-%eb%ac%b8%ed%99%94%ec%98%88%ec%88%a0-%eb%8b%a4%ec%a4%91%ec%9d%b4%ec%9a%a9%ec%8b%9c%ec%84%a4-%ec%9e%84%ec%8b%9c%ed%9c%b4%ea%b4%80-%ec%a2%85%eb%a3%8c-%eb%b0%8f-%ea%b0%9c/)), 반복 규칙("매월 둘째·넷째 일요일"), 부분 휴관(수영장만), 다중 시설 공지, 취소·연장 공지, "입장마감" 시간 혼동이다(전부 [추론]).

방어는 겹겹으로 쌓는다. 이 구성은 필자의 설계안이며 각 기법을 개별 근거로 지지하는 연구는 없다.

1. 정규식·키워드 선행 처리.
2. LLM에는 게시일(posted_date)을 주입하고, "연도·날짜는 텍스트와 게시일로 도출 가능할 때만, 아니면 null"을 지시하며 `unknown` 선택지를 허용한다(Anthropic은 "모른다" 허용이 거짓 정보를 크게 줄일 수 있다고 안내, [문서](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations)).
3. 필드마다 **원문 인용(evidence)** 을 요구한다.
4. **결정론적 검증**: 인용이 정규화된 원문의 부분 문자열인가, 출력의 모든 날짜·숫자가 인용에도 있는가, 시작일 ≤ 종료일, 기간이 상식 범위인가, 시설명이 알려진 암장 ID와 매칭되는가. 반복 규칙은 LLM이 아니라 코드가 제한된 enum으로 전개한다.
5. 두 번 추출해 필드가 다르면 검수로 보낸다.
6. 자기 보고 신뢰도 숫자는 믿지 않고 범주형 플래그와 규칙 불일치를 검수 트리거로 쓴다.

**프롬프트 인젝션**: 스크랩한 공지는 신뢰할 수 없는 입력이다. LLM 작업에 비밀·도구·쓰기 권한을 주지 않고, 출력은 스키마로 제한하며, 숨겨진 요소·HTML 주석은 제거하고, 마지막은 사람이 승인한다([Anthropic Mitigate jailbreaks](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks), [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/), 후자는 요약 경유). 이 앱에서의 주된 피해는 도구 남용이 아니라 거짓 사실이 데이터에 들어가는 것이므로 사람 승인이 가장 강한 통제다.

**정답 세트와 지표**: 과거 공지 100~200건을 층화 표집한다(실제 휴관·시간 변경 약 40%, 반복 규칙 20%, 다중 시설 15%, 부정·재개·취소 15%, 무관 10%). 안전 지표는 "영향 있는 공지를 놓치지 않았는가(재현율)"이고, 그 외 필드별 정확 일치율, 인용 유효율, 시설 귀속 오류를 본다. 통계적으로 n=100에서 오류 0건이어도 95% 상한은 약 3%(3/n 규칙)라서 "몇 퍼센트 아래일 가능성이 높다" 이상은 못 말한다. 그래서 안전 필드의 사람 검수는 유지한다(전부 필자 계산·[추론]). 모델·프롬프트를 바꿀 때마다 정답 세트로 회귀 시험하고, 검수자의 수정은 새 정답으로 쌓는다.

## 11. 결론

이 조사의 결론은 "무엇을 자동화할지"보다 "어디서 자동화를 멈출지"에 있다. 감지는 싸고 합법적인 영역이 넓지만, 값의 게시는 LLM 정확도를 측정하지 못한 지금 사람이 승인해야 한다. 자동화의 이득은 63곳을 돌아다니는 시간 절감이지 사람 판단의 제거가 아니다. 그리고 인스타그램 중심 암장이라는 구조적 사각지대는 기술이 아니라 암장 운영자 제보 채널로 메워야 한다.

따라서 지금 가장 값어치 있는 일은 코드를 쓰기 전에 §10의 실험 1~4를 끝내는 것이다. 한국 IP 차단 여부, 자동화 가능한 소스의 개수, 정답 세트가 모든 설계 결정의 입력이다. 그 결과가 나쁘면 "링크 제공 + 제보"로 후퇴하는 비용이 매우 낮다는 점이 이 설계의 안전판이다.
